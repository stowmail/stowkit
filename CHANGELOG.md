# Changelog

Changes to StowKit and the `stowmail` command-line tool, newest first. Security fixes rated Medium or worse also get a GitHub security advisory; Low ones are listed here only (see [SECURITY.md](SECURITY.md)).

## Unreleased

### Security

- **Informational:** for a Microsoft account, the "known billing sender" label (I-08) accepted a topmost `Authentication-Results` field with no authserv-id, the form in Microsoft's published examples, which any sender can write, for example someone in the same organisation, whose mail can arrive without Microsoft adding a field of its own above theirs. Real Outlook.com and Exchange Online fields both start with `mx.microsoft.com`, so `ProviderAuthentication.dmarc` now requires that authserv-id and gives no result without it. Protection was never affected; only the label's wording.

### Fixed

- The "known billing sender" label (I-08) never showed for Microsoft mail as delivered: Outlook.com and Exchange Online start their `Authentication-Results` field with the authserv-id and a version number (`mx.microsoft.com 1;`), which was refused. It is now read; an authserv-id may be followed only by a version number, for Gmail too. `dmarc=bestguesspass` (no DMARC policy published) is not a pass. Protection was never affected.

### Added

- Archive schema `v3`: a column for the provider's DMARC result on each email (`messages.sender_dmarc`), for the "known billing sender" label, and an index of the emails not yet checked. Opening an archive with this version upgrades it in place, adding the column and the index only (about 2 seconds for 40,000 emails); every stored email keeps its meaning and reads as not yet checked. Nothing fills the column yet. Older versions still open an upgraded archive and write to it.

## 0.1.3 (30 October 2026)

### Security

- **Low:** the sign-in listener on 127.0.0.1 ended the sign-in on the first `GET /` it received, whatever it carried, so a web page in any browser that sent `http://127.0.0.1:<port>/?error=x` across the port range could cancel a sign-in in progress (second review A-06). No token could be obtained this way (PKCE). Only a reply carrying the sign-in's `state`, compared in constant time, now ends it, with its code or the provider's own error; any other request gets a 400 page that says nothing about the sign-in and echoes nothing, and the listener keeps waiting until its 5-minute timeout. A connection that has not sent its request within 10 s is closed. `LoopbackError.stateMismatch` is no longer produced.
- **Low:** `stowmail` read app configuration (the OAuth client IDs) from `.env` in the current folder when `STOW_ENV_FILE` was not set, and `daemon install` saved that path for the background sync, so running it inside a downloaded folder could silently swap in someone else's client IDs and show their consent screen (second review A-08). Source builds now read only the file named by `STOW_ENV_FILE`, or else `~/Library/Application Support/Stow/config.env`; environment variables still override the file. A build made with `scripts/bundle-config.sh` and `-DSTOW_BUNDLED_CONFIG` has the IDs built in and reads no file or variable. `daemon install` no longer saves `./.env`; it keeps a saved `STOW_ENV_FILE` that still exists and drops one that does not. `doctor` names where the configuration came from. **If you kept your IDs in `engine/.env`, move them to `config.env` or set `STOW_ENV_FILE`.** `AppConfig.load` and `report` take `home:` and `bundled:` instead of `currentDirectory:`; `report` returns `AppConfig.Report`; `AppConfigError` cases carry where the value was looked for.
- **Low:** a token refresh that was in flight when `stowmail account remove` deleted the account's tokens (for example during `folders` or `verify --server`) saved the new tokens afterwards, adding the deleted Keychain item back, and a disconnected account's tokens were still refreshed (second review A-12). A refresh now replaces the tokens only in an item that still exists (`KeychainStore.update`, which never creates one, through `TokenStore.replace`) and only while the account is connected; otherwise the new tokens are dropped. A disconnected account is refused with the new `SyncError.accountRemoved` before any network or Keychain access. Signing in (`account add`, `account signin`) still adds or replaces. Existing Keychain items are not changed.
- **Low:** an error that reached the top of a `stowmail` command was printed by ArgumentParser as `Error: <error>` without going through `Redact.scrub`, so a database or mail-server error carrying an address, a token-shaped string or a line break reached the terminal and launchd's log as it was (second review A-14). `stowmail` now has its own `main`: ArgumentParser's own errors (help, version, usage, validation, `CleanExit`, `ExitCode`) keep their text and exit status, and anything else is printed scrubbed and on one line (`TopLevelError.line`, exit status 1). New `Redact.oneLine` shows CR, LF and tab as `\r`, `\n`, `\t` and other control, line-separator and bidi characters as `\u{XX}`.
- **Low:** log lines kept CR, LF and other control characters from the text they quoted, so a mail server's reply could start what looked like a new log line in `stowmail.log` or on standard error; metadata keys were not scrubbed; and a log folder or `stowmail.log` that already existed kept whatever permissions it had (second review A-15). Each log line now scrubs the message, every metadata key and value and the label, then escapes them with `Redact.oneLine`, so one event is one line. The first write in each process sets the folder to 0700 and the file to 0600.
- **Low:** `stowmail mcp log` printed each audit entry's client name, tool name and arguments as an assistant sent them, so an assistant steered by an email could put terminal escape sequences (erase the line, write the clipboard with OSC 52), line breaks or bidi controls in front of whoever reads the log (second review A-16). Each printed field now goes through the reply sanitiser (`ArchiveTools.oneLine`); the line is built by `MCPAuditEntry.printedLine`. The audit file itself is unchanged.
- **Low:** what an assistant read through `get_thread`, `search_messages` and `get_attachment` could carry text hidden in invisible characters (Unicode tag characters, runs of variation selectors, Hangul fillers), so an email could give an assistant instructions that the person reading it cannot see (second review A-17). Single-line fields dropped tag characters but kept selectors and fillers, and bodies and attachment text were not cleaned at all. `HiddenText` now removes Unicode's default-ignorable characters (and U+FFF9 to U+FFFB) from bodies, attachment text and single-line fields, keeping a joiner or selector that does visible work (an emoji sequence, a Persian word); in bodies and attachment text each removed run becomes `[hidden characters removed: N]`. Single-line fields no longer turn every ZWJ and ZWNJ into a space. The archive itself is unchanged.
- **Low:** search had no cost limits: a query of any length or number of words, and one-character prefixes such as `a*`, went to the full-text index as they were, so an OR of 32 one-letter prefixes took over a second on 3,000 messages and one of 100 or more words failed with an FTS5 parser stack overflow (second review A-18). `SearchLimits`, applied in `FTSExpression.build` and so for the CLI, the assistant tools and the app, now searches only the first 1 KB and 32 words and drops a `*` after fewer than two characters. `SearchQuery.limitsApplied` says what was cut, and `stowmail search` and `search_messages` print it.
- **Low:** the protection lists that keep invoices and other important mail out of removal suggestions failed open: a missing, broken or incomplete `rules-data.json` quietly became empty lists, so a billing email carrying strong bulk signals could be suggested for deletion (second review A-19). Such a file is now refused (`RulesData.load(from:)`, `RulesDataProblem`): every message is kept, nothing is offered for removal, no signals are stored, and `rules`, `rules report`, `tidy` and `doctor` say why (`TidySummary.rulesProblem`). A test fails if a list in the shipped file is emptied.
- **Low:** saved `.eml` file names were cut at 120 characters, not bytes, so a subject in Japanese or emoji gave a name over 255 bytes, which a byte-limited volume (ext4, SMB, most NAS) refuses with a misleading error (second review A-21). `EmlFileName` now cuts names to 240 bytes of UTF-8, between characters, and `SafeFile.numbered` shortens the name to make room for its number.
- **Informational:** the archive key was turned into a hex `String` and sent as SQL text (`PRAGMA key`) on every connection, and the Keychain and recovery-bundle copies were never wiped (second review I-02). It is now held in `KeyBuffer` (a locked page, wiped on release) and handed to SQLCipher with `sqlite3_key`; the Keychain and recovery-bundle copies are wiped after use. Key derivation, the file format, Keychain items and the recovery bundle are unchanged. `Archive.open`, `ArchiveMover`, `DirectMCPArchive` and `KeyManager.loadDatabaseKey` take or return a `KeyBuffer`.
- **Informational:** anyone who knows a Message-ID can place their mail inside a conversation through `References`, where an assistant reading `get_thread` would take it for one of the parties (second review I-07). `MessageDetail.senderDomainNewToThread` is now set when the From domain appears in no From, To or Cc of an earlier message of the same conversation, and `get_thread` says so under the From line. It is worked out when read; no schema change.
- **Informational:** mail from an address on the billing list was labelled "a known billing sender" whoever sent it, though anyone can write that address in From (second review I-08). The label now needs the provider's own DMARC pass for the From domain, read from the topmost `Authentication-Results` field only (`ProviderAuthentication.dmarc`, `SenderDMARC`); otherwise the reason reads "Kept: from a billing address at <domain>." Protection itself is unchanged. Until the result is stored per message, the label shows only in `stowmail rules report`.

### Fixed

- The OCR benchmark (`Benchmarks.ocrDoesNotHurtImport`, run only with `STOW_BENCH=1`) no longer waits up to 120 s for background-priority OCR to get a core after the import, which failed once on a busy Mac. It stops its own OCR loop and takes the next item directly, and prints the load average with its figures.

## 0.1.2 (29 October 2026)

### Security

- **Medium:** making a new recovery key (`stowmail recovery-key rotate`, `create`, `init`) replaced the archive's recovery bundle, `keys.recovery`, before the new key had been confirmed. Stopping at the prompt (Ctrl-C, a closed terminal, three mistyped groups) left a bundle that only the unsaved key opened, and sync paused (second review A-04). A new key is now written as `keys.recovery.pending` and replaces `keys.recovery` only after it is confirmed; the confirmation is committed durably first, and both files and the folder are flushed to the drive (`F_FULLFSYNC`). A confirmation stopped before the rename is finished by the next writer. Until then the old key keeps working and sync carries on. A pending key nobody confirmed is deleted when the prompt gives up, and `status` and `doctor` mention one that is left. The file format is unchanged. [GHSA-89jf-8jp8-689x](https://github.com/stowmail/stowkit/security/advisories/GHSA-89jf-8jp8-689x).
- **Low:** two `stowmail init` runs at once, or the app and the CLI, could both find no archive keys in the Keychain and both save a pair, the second replacing the first (second review A-09). Archive keys are now added with `KeychainStore.add`, which never replaces an item: one caller makes the pair and the other is refused. `rotate` also refuses keys other than the ones the archive was opened with, and `confirm` refuses a bundle whose keys differ from them, compared by a SHA-256 digest in constant time rather than by keeping a copy of the keys. Existing Keychain items are not changed.
- **Medium:** encrypted message and attachment files were renamed into place without being flushed to disk, and a file already at its content address was reused without a check (second review A-05, first review L-5). After a power cut or kernel panic, a torn or empty attachment could be linked from every later message carrying it, so those messages could not be rebuilt, and a torn message file stopped that message from ever being archived. Each new file and its folder are now handed to the drive (`fsync`) and one write barrier (`F_BARRIERFSYNC`) per message puts them on disk before the rows that use them. An existing file is reused only if it authenticates (an attachment must also have its exact sealed size); a damaged one is replaced atomically, and the warning logs only a hash prefix and sizes. A first sync's import step takes about 1 ms longer per message. `EncryptedFileStore.write` gains `replacingDamaged`; `EncryptedFileStore` and `Archive.open` take a `DiskSync`. [GHSA-9gcv-3mm3-hw86](https://github.com/stowmail/stowkit/security/advisories/GHSA-9gcv-3mm3-hw86).
- **Low:** removing mail from the archive committed each batch of 200 and deleted its files straight away, while the commit reached the disk only at the next checkpoint (second review A-11). After a power cut the removed rows could come back pointing at deleted files. Each batch's commit is now synced with `F_FULLFSYNC` (`synchronous = FULL` for that transaction) before its first file is deleted. Removing 10,000 messages took 11.6 s before and 12.6 s after.
- **Low:** `stowmail archive-move` released the writer lock before asking whether to delete the old copy, so a background sync that had opened the old folder could sync mail into it, which the deletion then destroyed (second review A-10). The command now holds the lock until it ends, and leaves `moved-to.json` in the old folder, flushed, before switching. `Archive.open`, `createArchive` and `archive-location` refuse a folder with it and name the new place. The scheduler checks for it after opening and again after taking the lock, and `stowmail daemon run` then exits with status 75 so launchd starts it afresh at the new place. A background sync installed with `STOW_ARCHIVE_DIR` pinned to another folder is warned about before the switch. The move itself is now `ArchiveRelocation.move` in StowEngine; `Scheduler.run` returns why it stopped.
- **Low:** an mbox export that stopped part way (a missing or damaged stored file, a full disk, a kill) left a partial file under its final name, and the retry then failed because the file existed; "Export everything" stayed blocked until the user deleted it (second review A-20). `MboxExport.export` now writes under a hidden temporary name, flushes it and renames it into place without replacing anything (`RENAME_EXCL`), and removes the temporary file on any error. `SafeFile` gains `openTemporary(in:)` and `publishExclusively(_:as:)`.

### Added

- `stowmail doctor` prints the archive's schema version and the newest this build knows (`ArchiveSchema.versionSummary`); an archive written by a newer build is shown as such.

### Fixed

- `swift test -c release -Xswiftc -enable-testing` compiles again, so the benchmarks run. The iCloud sign-in tests, which need a debug-only plain-text test endpoint (D-471), are left out of release builds. `scripts/check.sh` now builds the tests in release too (locally only; on the CI runner it took over 4 minutes).

## 0.1.1 (29 October 2026)

### Security

- **Medium:** one attachment that crashed or hung Apple's image or PDF readers stopped text recognition (OCR) for good, and an email whose reading crashed or hung Stow was tried again on every sync (second review A-03, the part not in 0.1.0). Each import and each OCR item is now counted before it is read. After three tries that never finished, an email is stored whole exactly as received and marked "couldn't read all of this email", and an attachment is marked unreadable; archiving and OCR move on. Reading one email has a 5-minute limit and one OCR item a 10-minute limit. Marked text is tried again only by a newer version. `stowmail status`, `doctor` and `verify` count these emails, and `MessageDetail.textIncomplete` and `AttachmentInfo.textUnreadable` carry the mark. [GHSA-39ch-8w9v-qg3p](https://github.com/stowmail/stowkit/security/advisories/GHSA-39ch-8w9v-qg3p).

- **Low:** `AddressListParser.parse` and `AddressListParser.messageIDs` never returned when the string held a CR LF (`"a\r\nb"` was enough), and used memory until the process was stopped. Swift reads CR LF as one character, which the tokeniser did not move past. Email could not trigger this: header values never contain a line feed by the time they reach the parser. Only code calling these functions directly could. Found by fuzzing (second review A-22).

### Added

- GitHub Actions: build, tests and gitleaks on every push to `main` (the required `check`), CodeQL, and a short fuzzing pass.
- Fuzz targets for HTML to text, encoded words and address lists, the search query parser, the ZIP reader and IMAP reply assembly, with 1 MB inputs (`scripts/fuzz.sh`).
- Archive schema `v2`: columns for marking an email whose text could not all be read, and for counting import, re-parse and text extraction attempts. Opening an archive with this version upgrades it in place, adding columns only (about 2 seconds for 40,000 emails); every stored email keeps its meaning, and older versions still open an upgraded archive.

## 0.1.0 (28 October 2026)

First tagged release.

### Security

- **High:** a crafted email could stop archiving: converting its HTML to text, or decoding its headers' encoded words, took time proportional to the square of its size. [GHSA-xhg9-88xv-2q76](https://github.com/stowmail/stowkit/security/advisories/GHSA-xhg9-88xv-2q76).
- **Low:** a mail server could hold sync without limit. Each IMAP command now has a byte limit and a deadline, replies for messages not asked for are dropped, and one stuck account no longer holds up the others.
- Text read from each part of an email is capped at 10 MB, and PDF text extraction has a 30-second limit.
